Running a validator is an ongoing commitment. This page is your day-two reference. It covers the configuration files, health monitoring, rewards, jail recovery, metadata changes, governance, and safe upgrades.

<Warning>
Double signing is catastrophic. If two instances of your validator sign conflicting blocks at the same height, the network permanently tombstones your validator and slashes its stake. Always confirm the old `lumerad` process has fully stopped before starting a new one, especially during upgrades or migrations.
</Warning>

## Configuration files

After `lumerad init`, three files live under `~/.lumera/config/`. Each controls a different layer.

| File | Layer |
|---|---|
| `config.toml` | CometBFT engine, peers, mempool, RPC |
| `app.toml` | Cosmos SDK application, gas, APIs, pruning |
| `client.toml` | Defaults for the `lumerad` CLI |

Restart `lumerad` after editing any of them. Changes only take effect when the process reloads.

### Peers in config.toml

```toml
# Seed nodes for initial peer discovery. Contacted once at startup.
seeds = "f64b9efc5747cc3556bdc281dab930a716dd63af@seeds.lumera.io:26656"

# Peers your node always keeps connected. Use for your own sentries.
persistent_peers = ""

# Connection limits
max_num_inbound_peers = 40
max_num_outbound_peers = 10
```

In a sentry architecture the validator leaves `seeds` empty and lists only its sentries in `persistent_peers`. The sentries use the public seeds and point `persistent_peers` at the validator's internal address. Sentries benefit from a higher inbound limit (100 or more) since they are the public face of your setup.

### RPC binding in config.toml

```toml
[rpc]
laddr = "tcp://127.0.0.1:26657"
```

Never expose the RPC port of a validator to the public internet. Bind it to `127.0.0.1` or a private interface.

### Gas, pruning, and APIs in app.toml

```toml
# Reject transactions below this gas price
minimum-gas-prices = "0.025ulume"

# Pruning strategy. Options are default, nothing, everything, custom
pruning = "default"
pruning-keep-recent = "100"   # custom only
pruning-interval = "10"       # custom only

# State sync snapshots offered to peers. 0 disables.
snapshot-interval = 1000
snapshot-keep-recent = 2
```

| Pruning strategy | What it keeps | Disk usage |
|---|---|---|
| `default` | The last 362,880 states (about 21 days) plus every 10,000th state | Medium |
| `nothing` | Everything, a full archive node | Very high |
| `everything` | Only the last 2 states | Lowest |
| `custom` | Whatever your two custom keys say | Configurable |

Archive nodes serve indexers and explorers well but need several times more disk. Do not run one on your validator unless you have the capacity.

```toml
[api]
enable = true
address = "tcp://0.0.0.0:1317"

[grpc]
enable = true
address = "0.0.0.0:9090"

[json-rpc]
enable = true
address = "0.0.0.0:8545"
ws-address = "0.0.0.0:8546"
```

The `[json-rpc]` section is the EVM endpoint added by the v1.20.0 upgrade. The [node EVM config guide](https://github.com/LumeraProtocol/lumera/blob/master/docs/evm-integration/user-guides/node-evm-config-guide.md) documents every EVM key in depth. A pure validator can disable all external API servers. Fewer open ports mean less attack surface.

### CLI defaults in client.toml

```toml
chain-id = "lumera-mainnet-1"
node = "tcp://localhost:26657"
output = "json"
keyring-backend = "os"
```

Setting `output = "json"` makes `lumerad` easy to pipe through `jq` in scripts.

### Ports

| Port | Service | Config key |
|------|---------|-----------|
| 26656 | P2P peer communication | `config.toml` `[p2p].laddr` |
| 26657 | CometBFT RPC | `config.toml` `[rpc].laddr` |
| 1317 | REST API (LCD) | `app.toml` `[api].address` |
| 9090 | gRPC | `app.toml` `[grpc].address` |
| 8545 | EVM JSON-RPC over HTTP | `app.toml` `[json-rpc].address` |
| 8546 | EVM JSON-RPC over WebSocket | `app.toml` `[json-rpc].ws-address` |

On a validator only port 26656 normally needs to be publicly reachable. Firewall the rest or bind them to `127.0.0.1`.

## Faster sync options

Two methods avoid replaying the whole chain from block 1.

State sync uses the built in CometBFT protocol. The node fetches a verified state snapshot from trusted RPC servers and then catches up on recent blocks.

```toml
[statesync]
enable = true
rpc_servers = "https://rpc1.lumera.io:443,https://rpc2.lumera.io:443"
trust_height = 1500000
trust_hash = "<block-hash-at-trust-height>"
trust_period = "168h"
```

Snapshot sync downloads a compressed database snapshot and places it under `~/.lumera/data/`. It is often faster for large chains but requires trusting the snapshot provider. Whichever method you use, always verify the `genesis.json` SHA-256 hash against the [lumera-networks repository](https://github.com/LumeraProtocol/lumera-networks) first.

## Run as a systemd service

A `systemd` unit keeps `lumerad` running through crashes and reboots.

```ini /etc/systemd/system/lumerad.service
[Unit]
Description=Lumera Protocol Node
After=network-online.target
Wants=network-online.target

[Service]
User=lumera
ExecStart=/usr/local/bin/lumerad start --home /home/lumera/.lumera
Restart=on-failure
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

```shell
sudo systemctl daemon-reload
sudo systemctl enable lumerad
sudo systemctl start lumerad
sudo journalctl -u lumerad -f
```

## Check validator health

Query bonding status, voting power, and commission at any time.

```shell
lumerad query staking validator $(lumerad keys show <key-name> --bech val -a)
```

Check sync state and block height.

```shell
lumerad status 2>&1 | jq .SyncInfo
```

A healthy node reports `"catching_up": false` with a height matching the chain tip on the [Lumera Portal](https://portal.lumera.io/lumera-mainnet-1).

```shell
# Missed blocks in the current signing window
lumerad query slashing signing-info $(lumerad tendermint show-validator)

# Active validators sorted by voting power
lumerad query staking validators --status BOND_STATUS_BONDED -o json | jq '.validators | sort_by(-.tokens)'

# Peer count
lumerad net_info 2>&1 | jq '.result.n_peers'
```

### Metrics worth alerting on

| Metric | Alert when |
|--------|-----------|
| Block signing rate | Below 95 percent of the window |
| Sync status | `catching_up` is true for more than 5 minutes |
| Peer count | Below 5 |
| Free disk | Below 20 percent |
| Memory usage | Above 90 percent |
| Missed blocks counter | Trending upward |
| Process uptime | Any unexpected restart |

Grafana with Prometheus plus [tenderduty](https://github.com/blockpane/tenderduty) or [cosmos-validator-watcher](https://github.com/kilnfi/cosmos-validator-watcher) covers dashboards and paging. At minimum, alert on missed blocks. Catching downtime early is the difference between a small penalty and a jail event.

## Withdraw rewards

Rewards accumulate in the distribution module until you withdraw them.

```shell
lumerad tx distribution withdraw-rewards <validator-address> \
  --commission \
  --from=<key-name> \
  --chain-id=lumera-mainnet-1 \
  --fees=5000ulume
```

The `--commission` flag includes your operator commission. Without it only self delegation rewards are withdrawn. Leave enough LUME in the account for future fees.

## Unjail after downtime

The chain jails a validator that misses too many blocks in the slashing window. A jailed validator earns nothing and leaves the proposer rotation. Fix the root cause first, then submit the unjail transaction.

```shell
lumerad tx slashing unjail \
  --from=<key-name> \
  --chain-id=lumera-mainnet-1 \
  --fees=5000ulume
```

<Warning>
A tombstoned validator cannot unjail. Tombstoning comes from double signing and is permanent. Check the `tombstoned` field in `lumerad query slashing signing-info` before assuming downtime was the cause.
</Warning>

Watch your signing rate closely for several hours after unjailing.

## Edit validator metadata

Update your public information or adjust commission with `edit-validator`. Include only the flags you want to change.

```shell
lumerad tx staking edit-validator \
  --moniker="new-moniker" \
  --website="https://yoursite.com" \
  --identity="<keybase-pgp-fingerprint>" \
  --security-contact="security@yoursite.com" \
  --details="Professional validator for Lumera Protocol" \
  --from=<key-name> \
  --chain-id=lumera-mainnet-1 \
  --fees=5000ulume
```

Commission changes are capped by the `commission-max-change-rate` you set at creation, per 24 hour period. A larger change fails.

## Vote on governance

Your vote carries your total delegated stake, and delegators who do not vote inherit it. Voting is part of the job.

```shell
lumerad tx gov vote <proposal-id> yes \
  --from=<key-name> \
  --chain-id=lumera-mainnet-1 \
  --fees=5000ulume

# Other options are no, abstain, no_with_veto
lumerad query gov vote <proposal-id> <your-address>
```

## Upgrade lumerad

Upgrades are coordinated through governance. When a software upgrade proposal passes, the chain halts at the planned height and waits for new binaries. The current release is `v1.20.1-hotfix`. If your validator predates v1.20.0, read the [EVM upgrade page](/upgrades/evm-upgrade) first, because the operator key migration is separate from the binary upgrade.

<Steps>

### Watch for upgrade proposals

```shell
lumerad query gov proposals --status voting_period
lumerad query gov proposal <proposal-id>
```

The `plan.height` field of a software upgrade proposal is the halt height.

### Pull the new release

```shell
cd ~/lumera
git fetch --tags
git checkout v<new-version>
```

### Rebuild and install

```shell
make build
sudo systemctl stop lumerad
sudo mv build/lumerad /usr/local/bin/lumerad
lumerad version
```

### Restart and watch

```shell
sudo systemctl start lumerad
sudo journalctl -u lumerad -f
```

Confirm the node resumes signing at the upgrade height without errors.

</Steps>

<Warning>
Stop the running process before replacing the binary. Follow stop, replace, start. Swapping the binary under a live process risks state corruption.
</Warning>

## Protect your keys

`~/.lumera/config/priv_validator_key.json` is the consensus key that signs blocks. An attacker holding it can double sign as you and get you tombstoned.

- Store it on an encrypted volume and set `chmod 600` on the file.
- Keep an offline backup and test restoring it before going live.
- High value validators should consider a remote signer such as [Horcrux](https://github.com/strangelove-ventures/horcrux) to keep the key off the node entirely.
