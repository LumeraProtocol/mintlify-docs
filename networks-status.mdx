Chain versions and upgrade heights change, and any value written into a page goes stale. This page records the current state with a timestamp, and every figure here is one command away from being re-checked.

## Check it yourself

These queries are the source of truth. Run them before relying on anything below.

<CodeGroup>

```bash Mainnet
# running version and height
curl -s https://rpc.lumera.io/abci_info | jq -r '.result.response | "\(.version) at height \(.last_block_height)"'

# scheduled upgrade, null when none is on chain
curl -s https://lcd.lumera.io/cosmos/upgrade/v1beta1/current_plan | jq .
```

```bash Testnet
curl -s https://lumera-testnet-rpc.polkachu.com/abci_info | jq -r '.result.response | "\(.version) at height \(.last_block_height)"'

curl -s https://lumera-testnet-api.polkachu.com/cosmos/upgrade/v1beta1/current_plan | jq .
```

</CodeGroup>

From a synced node, `lumerad status` and `lumerad query upgrade plan` return the same information.

## Next upgrade

Neither network has an upgrade plan on chain. `current_plan` returns `null` on both.

The mainnet EVM upgrade (Aurora Convergence, the `v1.20.x` line) was planned for block `6,715,000` and did not execute; mainnet passed that height on `v1.12.0`. It has been rescheduled and the new date is to be announced. See [the EVM upgrade](/upgrades/evm-upgrade).

```bash

```

<Warning>
  Build your node from a tag that carries every handler your target network has already applied. A binary missing a handler halts at that upgrade height and cannot sync past it. Testnet has applied `v1.20.2`, so a testnet node needs `v1.20.2` or newer.
</Warning>
