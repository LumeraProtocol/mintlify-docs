Validators are the backbone of Lumera Protocol. A validator node takes part in consensus through CometBFT. It proposes new blocks, signs votes, and keeps the network in agreement. In return you earn staking rewards from transaction fees and block emissions. You also vote on governance proposals that shape the protocol, from parameter changes to software upgrades.

<Note>
The `v1.20.0` EVM upgrade changed how validator operator keys are derived. If you ran a validator before the upgrade, follow the [EVM upgrade guide](/upgrades/evm-upgrade) to migrate your operator account. Your consensus key is not affected.
</Note>

## What validators do

Lumera uses CometBFT (formerly Tendermint Core) for Byzantine Fault Tolerant consensus. At each block height a proposer is selected from the active validator set, weighted by voting power. The proposer bundles transactions into a block. The remaining validators sign pre-votes and pre-commits. A block is final once more than two thirds of the total voting power has committed to it. This gives Lumera instant finality with no forks.

Your responsibilities as a validator.

- **Stake LUME.** Self-delegate `ulume`, the base denomination of LUME, to enter the active set and back your honesty with economic collateral.
- **Propose and sign blocks.** Stay online and responsive. Missing too many votes leads to downtime slashing.
- **Vote on governance.** Proposals alter chain parameters, fund the community pool, or trigger software upgrades.
- **Run a SuperNode (optional).** SuperNodes extend validators with storage and content authentication services for extra rewards. See the [SuperNode overview](/supernodes/overview).

## Validator and sentry architecture

Running a validator directly exposed to the public internet creates an attack surface. A DDoS flood against your IP can knock you offline and cause downtime slashing. The recommended mitigation is a sentry node architecture.

- **Validator node.** Your signing machine. Keep it on a private network, reachable only by your sentry nodes. Never expose its P2P or RPC port to the public internet.
- **Sentry nodes.** Public full nodes that relay blocks and transactions between your validator and the wider network. Run at least two sentries in different data centers or cloud regions.

Your validator connects to its sentries through `persistent_peers` in `config.toml`. The sentries connect to the broader network through `seeds` and open peer slots. If a sentry is attacked, you can rotate it without exposing your validator's IP.

## Hardware requirements

Both validator and sentry nodes have demanding I/O and memory requirements. The table lists the minimum recommended specifications for mainnet. Testnet runs on lighter hardware, but practicing on production grade machines reduces surprises at launch.

| Component | Validator node | Sentry node |
|-----------|----------------|-------------|
| CPU | 8 cores | 8 cores |
| Memory | 64 GB | 64 GB+ |
| Storage | 2 TB | 2 TB |
| Network | 5 Gbps+ | 5 Gbps+ |

Use NVMe SSDs for storage. Mechanical drives and even SATA SSDs struggle with the random read and write patterns of a live CometBFT node under load. Storage growth depends on pruning settings. A default pruned node grows at roughly 50 to 100 GB per month on an active mainnet.

## Software prerequisites

Install these tools before you build `lumerad`.

| Dependency | Purpose | Notes |
|------------|---------|-------|
| Go 1.26+ | Compile `lumerad` from source | Check `go.mod` in the repo for the exact version pin |
| Git | Clone the Lumera repository | Any recent version |
| make | Run the build targets in the Makefile | Usually pre-installed on Linux |
| libwasmvm | CosmWasm execution engine | Built by `make build` and must match the version in `go.mod` |
| AWS CLI | Snapshot sync from S3 | Optional, no AWS account required |

If `libwasmvm` is missing at runtime, download the matching `.so` file from the [CosmWasm releases](https://github.com/CosmWasm/wasmvm/releases) page and place it in `/usr/lib/` or wherever your dynamic linker looks.

## Validator lifecycle

Every validator follows the same progression from bare metal to active signing.

1. **Install.** Build `lumerad` from source and place the binary on your `$PATH`.
2. **Initialize.** Run `lumerad init` to create the home directory, generate node keys, and write default config files.
3. **Join and sync.** Download the network's `genesis.json` for mainnet or testnet, configure seeds, then sync the chain.
4. **Register.** Fund a key and submit a create-validator transaction to enter the active set.
5. **Operate.** Monitor uptime, apply upgrades on time, vote on proposals, and withdraw rewards.
