This guide takes you from an active validator to a registered, running SuperNode. You install the `supernode` binary, initialize it with your key, fund and delegate the SuperNode account, register on chain, and verify everything works.

## Ports

Open these ports before you start. The gRPC port serves clients. The P2P port connects you to other SuperNodes.

| Port | Protocol | Purpose | Exposure |
|------|----------|---------|----------|
| 4444 | TCP | SuperNode gRPC service | Public, clients connect here |
| 4445 | TCP | SuperNode P2P network | Public, peers connect here |
| 9090 | TCP | Your node's gRPC endpoint | Private, only the SuperNode process needs it |

<Warning>
Do not change the P2P port from `4445`. The network expects all SuperNodes on this port. A different port prevents peer connections and causes action failures.
</Warning>

<Steps>

### Confirm prerequisites

- Your validator is bonded and synced. See the [validator setup guide](/validators-mainnet/node-setup) if not.
- Your firewall allows inbound traffic on `4444` and `4445`.
- You know your validator operator address. Retrieve it on the validator host with `lumerad keys show <key-name> --bech val -a`.

### Install the binary

Download the latest release from the [SuperNode releases page](https://github.com/LumeraProtocol/supernode/releases). The latest stable release is `v2.5.2`, with `v2.6.1-testnet` available for testnet.

```shell
curl -L https://github.com/LumeraProtocol/supernode/releases/download/v2.5.2/supernode-linux-amd64 \
  -o /usr/local/bin/supernode

chmod +x /usr/local/bin/supernode
supernode version
```

### Initialize the SuperNode

`supernode init` writes `~/.supernode/config.yml` and sets up the keyring. The interactive wizard prompts for every value. For production and scripted deployments, pass flags and keep the passphrase in an environment variable.

<Warning>
Never pass `--mnemonic` on a command line in production. Shell history records it. Supply the mnemonic from a secrets manager or a file with `600` permissions, and clear your history after initialization.
</Warning>

<Tabs>
  <Tab title="Mainnet">
    ```shell
    export KEYRING_PASS="your-secure-passphrase"

    supernode init -y \
      --keyring-backend file \
      --keyring-passphrase-env KEYRING_PASS \
      --key-name mykey \
      --recover \
      --mnemonic "word1 word2 ... word24" \
      --supernode-addr 0.0.0.0 \
      --supernode-port 4444 \
      --lumera-grpc localhost:9090 \
      --chain-id lumera-mainnet-1
    ```
  </Tab>
  <Tab title="Testnet">
    ```shell
    export KEYRING_PASS="your-secure-passphrase"

    supernode init -y \
      --keyring-backend file \
      --keyring-passphrase-env KEYRING_PASS \
      --key-name mykey \
      --recover \
      --mnemonic "word1 word2 ... word24" \
      --supernode-addr 0.0.0.0 \
      --supernode-port 4444 \
      --lumera-grpc localhost:9090 \
      --chain-id lumera-testnet-2
    ```
  </Tab>
</Tabs>

The `--recover` flag imports a key from your mnemonic instead of generating a new one. Point `--lumera-grpc` at `localhost:9090` when the SuperNode shares a machine with your node, or at your node's address otherwise.

### Note your SuperNode account address

The registration steps need the SuperNode account address. Read it from the config.

```shell
supernode config list
```

The `identity` field under the `supernode` section shows the `lumera1...` address. This page calls it the SN account. You can also print it with `lumerad` on the SuperNode host.

```shell
lumerad keys show mykey -a --keyring-backend file --keyring-dir ~/.supernode/keys
```

<Note>
On the SuperNode host, every `lumerad` command needs both `--keyring-backend file` and `--keyring-dir ~/.supernode/keys`. The SuperNode keyring lives there, not in the default `lumerad` location.
</Note>

### Fund the SuperNode account

Registration uses a dual source stake model. Your validator self delegation and the SN account delegation add together, and the combined total must meet the on-chain minimum. Check the current minimum, because governance can change it.

```shell
lumerad query supernode params
```

Send LUME to the SN account from your validator wallet, or use the [faucet](/faucet) on testnet.

```shell
lumerad tx bank send <validator-key> <SN_ACCOUNT> <amount>ulume \
  --chain-id lumera-mainnet-1 \
  --gas auto --gas-adjustment 1.3 \
  --fees 5000ulume -y
```

### Delegate from the SuperNode account

Run this on the SuperNode host. It links the SN account stake to your validator. If the SuperNode host has no local chain node, point `--node` at your validator's RPC or a public endpoint.

```shell
VALOPER="lumeravaloper1..."   # your validator operator address

lumerad tx staking delegate "$VALOPER" <amount>ulume \
  --from mykey \
  --keyring-backend file \
  --keyring-dir ~/.supernode/keys \
  --chain-id lumera-mainnet-1 \
  --node tcp://<VALIDATOR_IP>:26657 \
  --gas auto --gas-adjustment 1.3 \
  --fees 7000ulume -y
```

Verify the delegation exists.

```shell
lumerad query staking delegations <SN_ACCOUNT> --node tcp://<VALIDATOR_IP>:26657
```

### Register on chain

Run this on the validator host, signed by the validator operator key. It cannot run from the SuperNode server.

```shell
VALOPER=$(lumerad keys show <validator-key> --bech val -a)
SN_ENDPOINT="<SN_PUBLIC_IP>:4444"
SN_ACCOUNT="lumera1..."

lumerad tx supernode register-supernode \
  "$VALOPER" \
  "$SN_ENDPOINT" \
  "$SN_ACCOUNT" \
  --from <validator-key> \
  --chain-id lumera-mainnet-1 \
  --gas auto --gas-adjustment 1.3 \
  --fees 5000ulume -y
```

A successful broadcast prints `code: 0`.

### Start the SuperNode

```shell
supernode start
```

For production, wrap the process in a `systemd` unit with `Restart=always` so it survives crashes and reboots. Pass `-d /path/to/dir` to run from a custom base directory.

### Verify everything

Check the on-chain record from the validator host.

```shell
lumerad query supernode get-supernode "$VALOPER"
```

The state should read `SUPERNODE_STATE_ACTIVE`. If the query returns nothing right after registration, wait a few blocks.

Confirm the ports are reachable from an external machine.

```shell
nc -zv <SN_PUBLIC_IP> 4444
nc -zv <SN_PUBLIC_IP> 4445
```

</Steps>
