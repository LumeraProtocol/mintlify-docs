Lumera Protocol is organized into four layers. The base chain provides consensus and three execution environments. Custom modules add storage, identity, and SuperNode coordination. The SuperNode layer does the heavy off-chain work. Client applications surface all of it to users. This page walks through each layer and how they interact.

```
┌─────────────────────────────────────────────────────┐
│                  Client layer                       │
│         Lumera Hub  ·  LumeScope  ·  CLI            │
├─────────────────────────────────────────────────────┤
│                 SuperNode layer                     │
│      Cascade (permanent storage)  ·  Sense (AI)     │
├─────────────────────────────────────────────────────┤
│              Custom module layer                    │
│  x/action  ·  x/supernode  ·  x/lumeraid  ·  x/claim│
├─────────────────────────────────────────────────────┤
│                   Base layer                        │
│   Cosmos SDK v0.53.6  ·  CosmWasm  ·  IBC  ·  EVM   │
└─────────────────────────────────────────────────────┘
```

## Base layer

The base layer handles block production, consensus, accounts, governance, and smart contract execution.

**Cosmos SDK v0.53.6** is the chain framework, the same one behind Cosmos Hub and Osmosis. It brings CometBFT consensus with fast finality, the standard modules (`x/bank`, `x/staking`, `x/gov`, `x/distribution`), and automatic gRPC and REST APIs for every module. The whole node ships as the single `lumerad` binary.

**CosmWasm** runs Rust smart contracts compiled to WebAssembly, sandboxed with deterministic gas metering.

**IBC** connects Lumera to other Cosmos chains for token transfers and arbitrary messages. Interchain accounts (ICS-27) let external chains drive Cascade remotely. See [interchain accounts](/cascade/concepts/interchain-accounts).

**Cosmos EVM** runs Solidity contracts with standard Ethereum tooling. It arrived with the v1.20.0 upgrade and is live on testnet, with the mainnet upgrade ahead. One private key operates both an EVM address (`0x...`) and a bech32 address (`lumera1...`). The [smart contracts overview](/smart-contracts) covers it in depth.

## Two node types

Lumera separates consensus from services.

**Validators** secure the chain through delegated proof of stake. They propose and sign blocks with CometBFT and vote on governance. See the [validator overview](/validators-mainnet/overview).

**SuperNodes** are companion daemons run by validators. They store files for Cascade, analyze content for Sense, and earn proof of service rewards from action fees. This split keeps consensus light while heavy compute and storage scale independently. See the [SuperNode overview](/supernodes/overview).

The chain is the control plane. It records requests, escrows fees, and tracks results. SuperNodes are the data plane. Files move directly between clients and SuperNodes and never pass through consensus.

## Custom module layer

Four custom modules implement the protocol logic. The EVM upgrade added support modules (`x/vm`, `x/feemarket`, `x/precisebank`, `x/erc20`, `x/evmigration`) documented on the [EVM upgrade page](/upgrades/evm-upgrade). This table is a map, not deep documentation. The linked pages cover the developer workflows.

| Module | What it does |
|---|---|
| `x/action` | Manages the lifecycle of Cascade and Sense actions from registration to approval |
| `x/supernode` | Registers SuperNodes, ranks the active top list, tracks metrics, and pays rewards |
| `x/lumeraid` | Anchors decentralized identities to Lumera addresses |
| `x/claim` | Handles token claims from the legacy Pastel Network |

### The action lifecycle

Every Cascade or Sense request is an action, an on-chain record with a state machine.

<Steps>
  <Step title="Register">
    A client submits the registration transaction. The service fee is locked in escrow and the action gets a unique ID. The state is `PENDING`.
  </Step>
  <Step title="Process">
    Top ranked SuperNodes pick up the action, receive the file over gRPC, and do the work. The state is `PROCESSING`.
  </Step>
  <Step title="Finalize">
    When the work completes and results are committed, the state becomes `DONE`. A failed or expired action becomes `FAILED` and the escrowed fee is refunded.
  </Step>
  <Step title="Approve">
    Where a flow requires explicit approval, an approval transaction moves the action to `APPROVED` and the escrowed fee pays out to the SuperNodes that served it.
  </Step>
</Steps>

The fee escrow makes storage trust free in both directions. You only pay when the network actually stores your file. Current Cascade parameters are 10000 `ulume` base plus 10 `ulume` per KB, about 0.02 LUME for a 1 MB file. Governance can change these parameters.

### SuperNode registry and ranking

The `x/supernode` module is the source of truth for SuperNode registrations. It stores each node's address, endpoint, and stake, maintains the ranked top list that `x/action` routes work to, and accounts for completed actions. A SuperNode must stay tied to an active validator. If the validator is jailed or unbonds, the SuperNode drops off the list.

## SuperNode layer

Each SuperNode runs the `supernode` binary alongside `lumerad`.

### Cascade

Cascade is permanent file storage with a pay once, store forever model. The SuperNode receives a file through its streaming gRPC endpoint, encodes it with RaptorQ erasure coding, and spreads the symbols across a Kademlia DHT. Any sufficiently large subset of symbols rebuilds the file, so the network self heals when nodes leave. Start with [how Cascade works](/cascade/how-cascade-works) and go deeper in [erasure coding](/cascade/concepts/erasure-coding).

### Sense

Sense is AI powered content authentication. SuperNodes compute a perceptual fingerprint of submitted media, a feature vector that captures what the content looks like rather than its exact bytes. They compare it against the network's registered assets and record a similarity verdict on chain. Slightly altered copies still match, which plain hashing cannot do.

Sense results include a similarity score between 0 and 1, the list of near duplicate candidates, and the fingerprint hash. All of it is permanently queryable, which makes Sense useful for originality checks, provenance records, and duplicate prevention in marketplaces. Sense actions cost less than Cascade because only the analysis result is stored, not the file.

### Identity with LumeraID

LumeraID anchors identity records to Lumera addresses through the `x/lumeraid` module. There is no separate username. Your address is your identity, and the record is controlled by your private key. The protocol uses it wherever ownership must be proven. Cascade downloads of private files require a signature that matches the registering identity, which is why files are private by default even though their encoded symbols live on a public network. Signatures follow ADR-036, the Cosmos standard for signing arbitrary data.

## Client layer

**Lumera Hub** is the official client for web, desktop, and mobile at [hub.lumera.io](https://hub.lumera.io). It covers balances, staking, storage, and identity. See the [Hub overview](/hub/overview).

**LumeScope** is a read-only REST API aggregator for developers who want decoded network state without running a node. It decodes action metadata, aggregates SuperNode metrics, and serves 16 endpoints with a Swagger UI. See the [LumeScope API reference](/api/lumescope).

**`lumerad`** is the chain binary and CLI. It runs nodes, manages keys, broadcasts transactions, and queries every module. See the [CLI reference](/sdk/lumerad-cli).

The [SDKs](/sdk/javascript) wrap the chain APIs and the SuperNode protocol for JavaScript and Go applications.
